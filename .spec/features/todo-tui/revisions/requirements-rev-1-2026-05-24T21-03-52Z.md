# todushka — Requirements

**Status:** Draft
**Author:** Claude (spec-driven-dev pipeline)
**Date:** 2026-05-25
**Feature:** todo-tui

## Overview

`todushka` — однопользовательский терминальный todo-менеджер на Go, повторяющий модель Things 3 (Inbox / Today / Upcoming / Anytime / Someday / Logbook / Trash + Areas + Projects + Tags + повторы + Quick Entry) с keyboard-first UX и локальным хранилищем. В v1 без сетевой синхронизации и интеграций с календарём; архитектура domain-слоя проектируется так, чтобы sync и интеграции добавлялись без переписывания ядра. Поставляется как один статический бинарь.

## Glossary

| Term | Definition | Code Artifact |
|------|------------|---------------|
| `Task` | Минимальная единица работы пользователя: заголовок, заметки, опциональные start date / deadline, теги, checklist, состояние (`open` / `completed` / `cancelled`), параметры повтора. | `internal/domain/task` |
| `Project` | Конечное начинание со списком задач, опциональным deadline, опциональной привязкой к `Area`, опциональными `Heading` для группировки задач внутри проекта. | `internal/domain/project` |
| `Area` | Долгоживущая сфера ответственности (Work / Home), агрегирующая проекты и независимые задачи; не имеет дедлайна. | `internal/domain/area` |
| `Heading` | Подзаголовок-разделитель внутри `Project`, группирующий задачи; не имеет дедлайна и не выполняется. | `internal/domain/project` |
| `Tag` | Плоский ярлык (v1): строковое имя, прикрепляемое к нескольким `Task`. Иерархия отложена на v2. | `internal/domain/tag` |
| `Checklist Item` | Подпункт внутри одной `Task` со своим состоянием `done` / `not done`, без отдельных дат и тегов. | `internal/domain/task` |
| `Inbox` | Системный список незаклассифицированных `Task`: те, у которых не задана ни `Area`, ни `Project`, ни start date, ни Someday-флаг. | `internal/domain/list` |
| `Today` | Системный список задач, считающихся актуальными на текущий локальный день. Правила формирования зафиксированы в REQ-8.x. | `internal/domain/list` |
| `Upcoming` | Системный список задач с start date в будущем, упорядоченных по дате. | `internal/domain/list` |
| `Anytime` | Системный список открытых задач без start date, привязанных к `Area` или `Project`, и не помеченных как Someday. | `internal/domain/list` |
| `Someday` | Системный список задач, явно отложенных пользователем. | `internal/domain/list` |
| `Logbook` | Системный список завершённых (`completed` / `cancelled`) задач, отсортированный по дате завершения. | `internal/domain/list` |
| `Trash` | Системный контейнер для удалённых задач/проектов до окончательной очистки. | `internal/domain/trash` |
| `Quick Entry` | Модальный диалог быстрого ввода задачи из любого экрана, поддерживающий inline-синтаксис (теги, дата, проект). | `internal/tui/quickentry` |
| `Today Engine` | Чистая функция, вычисляющая принадлежность задачи к списку `Today` по start date, deadline и явному «pin to today». | `internal/domain/today` |
| `Repeat Rule` | Описание правила повторения задачи (`daily`, `every N days`, `weekly on <weekdays>`, `monthly on <day>`). | `internal/domain/repeat` |
| `NextOccurrence` | Чистая функция, вычисляющая дату следующего экземпляра задачи на основе `Repeat Rule` и опорной даты. | `internal/domain/repeat` |
| `Repository` | Абстракция хранилища, не зависящая от выбора БД; реализуется поверх `bbolt` в v1. | `internal/storage` |
| `XDG Data Home` | Каталог данных пользователя по XDG Base Directory Specification (`$XDG_DATA_HOME`, fallback `~/.local/share`). | `internal/config` |

## User Stories

- Как **пользователь terminal-first**, я хочу записать мысль в Inbox одной горячей клавишей из любого экрана, чтобы не отвлекаться от текущей работы.
- Как **пользователь Things 3**, я хочу видеть привычные списки Today / Upcoming / Anytime / Someday в TUI, чтобы перенести существующий workflow в терминал без переучивания.
- Как **пользователь с множеством сфер жизни**, я хочу группировать проекты в Areas и переключаться между ними клавиатурой, чтобы не смешивать рабочее и личное.
- Как **пользователь с повторяющимися задачами**, я хочу, чтобы выполнение повторяющейся задачи автоматически создавало следующий экземпляр на корректную дату, чтобы не воссоздавать рутину вручную.
- Как **пользователь, работающий на macOS и Linux**, я хочу, чтобы приложение хранило данные в каталоге, соответствующем платформенным конвенциям (XDG / `$HOME/Library`), чтобы корректно бэкапиться вместе с остальными настройками.
- Как **скриптовый пользователь**, я хочу иметь не-интерактивные CLI-команды (`todushka add`, `todushka today`, `todushka complete`), чтобы автоматизировать ввод задач из других инструментов (Alfred, Raycast, скрипты в IDE).
- Как **пользователь с многолетней историей**, я хочу экспортировать всю БД в JSON и импортировать обратно, чтобы делать резервные копии и мигрировать между версиями без потери данных.
- Как **новый пользователь**, я хочу запустить `todushka` без предварительной настройки, чтобы база и каталоги создавались автоматически при первом запуске.

## Requirements

### Группа 1 — Quick Capture (Inbox + Quick Entry)

**REQ-1.1** WHEN пользователь нажимает глобальный хоткей Quick Entry в любом экране TUI, the system SHALL открыть модальный диалог ввода поверх текущего экрана, не теряя позиции пользователя в исходном списке.

**REQ-1.2** WHEN пользователь подтверждает ввод в Quick Entry непустой строкой, the system SHALL создать новую `Task` со статусом `open` и поместить её в `Inbox`, если в строке не указано иное.

**REQ-1.3** WHEN пользователь подтверждает ввод в Quick Entry пустой строкой или строкой только из пробелов, the system SHALL не создавать `Task` и закрыть диалог без ошибки.

**REQ-1.4** WHEN в строке Quick Entry присутствует токен `#<имя_тега>`, the system SHALL прикрепить к создаваемой `Task` соответствующий `Tag`, создавая его, если такого `Tag` ещё нет.

**REQ-1.5** WHEN в строке Quick Entry присутствует токен `@today`, the system SHALL установить у создаваемой `Task` start date равной текущему локальному дню.

**REQ-1.6** WHEN в строке Quick Entry присутствует токен `@<имя_проекта>`, the system SHALL привязать создаваемую `Task` к существующему `Project` с этим именем; при множественном совпадении SHALL отклонить ввод с понятным сообщением и не создавать `Task`.

**REQ-1.7** WHEN в строке Quick Entry присутствует токен `!YYYY-MM-DD`, the system SHALL установить у создаваемой `Task` deadline равным указанной дате.

**REQ-1.8** WHEN в строке Quick Entry указан некорректный токен (например, `!2026-13-40` или `@<несуществующий_проект>`), the system SHALL отклонить ввод, оставить диалог открытым с исходной строкой и показать сообщение об ошибке с указанием конкретного некорректного токена.

### Группа 2 — Системные списки

**REQ-2.1** WHEN пользователь открывает `Inbox`, the system SHALL показать все `Task` со статусом `open`, не привязанные ни к `Area`, ни к `Project`, без start date, не помеченные как Someday, отсортированные по дате создания в порядке убывания.

**REQ-2.2** WHEN пользователь открывает `Today`, the system SHALL показать все `Task`, удовлетворяющие правилам Today Engine (см. группу 8), сгруппированные по родительскому `Project`/`Area` с заголовками-разделителями.

**REQ-2.3** WHEN пользователь открывает `Upcoming`, the system SHALL показать все `Task` со статусом `open` и start date > текущего локального дня, сгруппированные по start date в порядке возрастания.

**REQ-2.4** WHEN пользователь открывает `Anytime`, the system SHALL показать все `Task` со статусом `open`, привязанные к `Area` или `Project`, не имеющие start date или с start date ≤ текущего локального дня, не помеченные как Someday.

**REQ-2.5** WHEN пользователь открывает `Someday`, the system SHALL показать все `Task` со статусом `open`, явно помеченные пользователем как Someday, независимо от привязки и дат.

**REQ-2.6** WHEN пользователь открывает `Logbook`, the system SHALL показать все `Task` со статусом `completed` или `cancelled`, отсортированные по дате завершения в порядке убывания, без ограничения по количеству в v1.

**REQ-2.7** WHEN пользователь открывает `Trash`, the system SHALL показать все `Task` и `Project`, помеченные как удалённые, с возможностью восстановления или окончательного удаления.

### Группа 3 — Areas

**REQ-3.1** WHEN пользователь выполняет действие «создать Area» с непустым именем, the system SHALL создать новую `Area` с этим именем; имена `Area` нечувствительны к регистру и SHALL быть уникальными в пределах БД.

**REQ-3.2** WHEN пользователь пытается создать `Area` с именем, совпадающим (нечувствительно к регистру) с существующей, the system SHALL отклонить операцию с сообщением о коллизии и не изменить состояние БД.

**REQ-3.3** WHEN пользователь удаляет `Area`, содержащую `Project` или независимые `Task`, the system SHALL запросить подтверждение и при подтверждении переместить все содержащиеся `Project` и `Task` в `Inbox` (потеряв привязку к `Area`).

**REQ-3.4** WHEN пользователь открывает `Area`, the system SHALL показать список её `Project` и независимых `Task` (тех, у которых задано `area_id`, но не задано `project_id`).

### Группа 4 — Projects и Headings

**REQ-4.1** WHEN пользователь создаёт `Project` с непустым названием, the system SHALL создать новый `Project` со статусом `open`, опциональной привязкой к `Area`, опциональным deadline, пустым списком задач.

**REQ-4.2** WHEN пользователь добавляет `Heading` внутрь `Project`, the system SHALL создать `Heading` как структурный элемент проекта, не имеющий собственного состояния, не входящий в Today / Logbook и не подсчитываемый в прогрессе проекта.

**REQ-4.3** WHEN все `Task` внутри `Project` имеют статус `completed` или `cancelled`, the system SHALL пометить `Project` как `completed` автоматически только если пользователь включил опцию «автозакрытие проекта»; иначе SHALL оставить статус без изменений.

**REQ-4.4** WHEN у `Project` задан deadline и текущая дата превышает deadline, при статусе `open`, the system SHALL отобразить визуальный индикатор «overdue» при показе проекта в любом списке.

**REQ-4.5** WHEN пользователь перемещает `Task` между `Project` или из `Project` в `Inbox`, the system SHALL обновить привязку `project_id` (и `area_id`, если требуется) без потери других полей задачи.

### Группа 5 — Task editing

**REQ-5.1** WHEN пользователь открывает редактирование `Task`, the system SHALL отобразить редактируемые поля: title, notes (multiline), start date, deadline, tags, checklist, repeat rule, и принадлежность (area/project/heading).

**REQ-5.2** WHEN пользователь сохраняет изменения `Task` с пустым title, the system SHALL отклонить сохранение и оставить экран редактирования открытым с подсветкой поля title и сообщением об ошибке.

**REQ-5.3** WHEN пользователь устанавливает у `Task` deadline раньше её start date, the system SHALL отклонить сохранение и показать сообщение о конфликте дат.

**REQ-5.4** WHEN пользователь добавляет к `Task` `Checklist Item`, the system SHALL сохранить пункт как часть задачи с состоянием `not done` по умолчанию.

**REQ-5.5** WHEN все `Checklist Item` задачи переведены в `done`, the system SHALL **НЕ** изменять статус самой `Task` автоматически (пользователь явно завершает задачу).

**REQ-5.6** WHEN пользователь завершает `Task` (статус → `completed`), the system SHALL зафиксировать `completed_at = now()` и переместить `Task` в `Logbook` (логически — изменение статуса; физически — `Task` остаётся в исходном `Project`/`Area`, но исключается из всех системных списков, кроме `Logbook`).

**REQ-5.7** WHEN пользователь отменяет `Task` (статус → `cancelled`), the system SHALL зафиксировать `cancelled_at = now()` и применить те же правила, что и для `completed`, кроме создания следующего экземпляра при наличии Repeat Rule (REQ-7.x).

### Группа 6 — Tags

**REQ-6.1** WHEN пользователь добавляет `Tag` к `Task`, the system SHALL создать `Tag` с указанным именем, если такого ещё нет; имена `Tag` нечувствительны к регистру и хранятся в нормализованном виде.

**REQ-6.2** WHEN пользователь удаляет `Tag` из БД полностью, the system SHALL отвязать этот `Tag` от всех `Task` и удалить запись о теге; задачи не удаляются.

**REQ-6.3** WHEN пользователь фильтрует список задач по нескольким `Tag`, the system SHALL вернуть задачи, имеющие **все** указанные теги (логическое AND); поведение OR-фильтрации не входит в v1.

**REQ-6.4** WHEN пользователь переименовывает `Tag`, the system SHALL обновить имя `Tag` глобально, сохранив привязку ко всем задачам; имя SHALL оставаться уникальным после переименования (нечувствительно к регистру), иначе операция отклоняется.

### Группа 7 — Repeating tasks

**REQ-7.1** WHEN пользователь задаёт у `Task` Repeat Rule одного из типов `daily`, `every N days` (N ≥ 1), `weekly on <weekdays>` (непустой набор дней недели), `monthly on <day-of-month>` (1..28 в v1; 29/30/31 — needs spike, см. §2.7), the system SHALL валидировать параметры и сохранить правило вместе с задачей.

**REQ-7.2** WHEN пользователь завершает `Task` со статусом `completed` при наличии Repeat Rule, the system SHALL создать новый экземпляр той же задачи (тот же title, notes, теги, project/area, checklist в исходном состоянии `not done`) со start date равной `NextOccurrence(rule, completed_at)`, а исходную задачу оставить в `Logbook`.

**REQ-7.3** WHEN пользователь отменяет `Task` (статус → `cancelled`) при наличии Repeat Rule, the system SHALL **НЕ** создавать следующий экземпляр.

**REQ-7.4** WHEN Repeat Rule имеет тип `monthly on <day-of-month>` со значением 29, 30 или 31, the system SHALL отклонить ввод в v1 с сообщением «monthly day-of-month > 28 will be supported in v2».

**REQ-7.5** WHEN Repeat Rule имеет тип `every N days` с N < 1 или `weekly on <weekdays>` с пустым набором дней, the system SHALL отклонить ввод с сообщением о невалидных параметрах правила.

### Группа 8 — Today Engine

**REQ-8.1** WHEN `Task` имеет статус `open` и start date ≤ текущему локальному дню, the system SHALL включить её в список `Today`.

**REQ-8.2** WHEN `Task` имеет статус `open`, не имеет start date, но имеет deadline ≤ текущему локальному дню + N (N = 0 по умолчанию, конфигурируется), the system SHALL включить её в список `Today` с визуальным индикатором «due».

**REQ-8.3** WHEN пользователь явно «закрепляет на сегодня» (`pin to today`) задачу со статусом `open`, the system SHALL включить её в `Today` независимо от start date и deadline до явного откреплеления или завершения.

**REQ-8.4** WHEN `Task` имеет start date в будущем (> текущего локального дня) и не помечена как pinned to today, the system SHALL **НЕ** включать её в `Today`.

**REQ-8.5** WHEN `Task` имеет статус `completed` или `cancelled`, the system SHALL **НЕ** включать её в `Today` независимо от других полей.

### Группа 9 — Хранилище и persistence

**REQ-9.1** WHEN приложение запускается впервые и каталог данных не существует, the system SHALL создать каталог `$XDG_DATA_HOME/todushka/` (или `$HOME/.local/share/todushka/` если `$XDG_DATA_HOME` не задана) и пустую БД внутри него.

**REQ-9.2** WHEN приложение запускается и БД уже существует, the system SHALL открыть её в режиме read-write, выполнив миграции схемы при необходимости (см. REQ-9.4).

**REQ-9.3** WHEN другой процесс уже удерживает блокировку файла БД, the system SHALL завершиться с кодом выхода != 0 и сообщением «Database is locked by another todushka process» в stderr, не повредив файл.

**REQ-9.4** WHEN версия схемы в БД меньше версии, поддерживаемой бинарником, the system SHALL применить все недостающие миграции в порядке возрастания версии и обновить запись `schema_version` в БД.

**REQ-9.5** WHEN версия схемы в БД больше версии, поддерживаемой бинарником, the system SHALL завершиться с понятным сообщением «Database schema version X is newer than this binary supports (Y). Upgrade todushka.» и кодом выхода != 0, не изменяя БД.

**REQ-9.6** WHEN любая операция мутации (`add`, `complete`, `edit`, `delete`) завершается успешно, the system SHALL гарантировать, что изменение зафиксировано на диске до возврата управления вызывающему (synchronous commit).

### Группа 10 — Export / Import

**REQ-10.1** WHEN пользователь выполняет `todushka export --json <path>` (или stdout, если path не задан), the system SHALL записать в файл/stdout полный snapshot БД в формате JSON, включающий все Areas, Projects, Tasks, Tags, Headings, Checklist Items, Repeat Rules и schema_version.

**REQ-10.2** WHEN пользователь выполняет `todushka import --json <path>`, the system SHALL заменить текущее содержимое БД содержимым из файла после явного подтверждения пользователем (или `--yes` флаг), при условии что schema_version в файле ≤ версии, поддерживаемой бинарём.

**REQ-10.3** WHEN импортируемый JSON-файл не валидируется по схеме экспорта или содержит несовместимую schema_version, the system SHALL отклонить импорт, оставить БД нетронутой и вывести сообщение об ошибке с указанием первой обнаруженной проблемы.

### Группа 11 — CLI scripting commands

**REQ-11.1** WHEN пользователь выполняет `todushka add "<title>" [флаги]`, the system SHALL создать `Task` с указанными атрибутами (флаги: `--project <name>`, `--area <name>`, `--tag <name>` (multi), `--start <date>`, `--deadline <date>`, `--someday`) без запуска TUI и вернуть код выхода 0 при успехе.

**REQ-11.2** WHEN пользователь выполняет `todushka today [--json]`, the system SHALL вывести в stdout содержимое списка `Today` (текстовый формат по умолчанию, JSON при флаге `--json`) и завершиться кодом 0.

**REQ-11.3** WHEN пользователь выполняет `todushka complete <task-id>`, the system SHALL перевести задачу в статус `completed` (с учётом Repeat Rule, REQ-7.2) и вернуть код выхода 0; если задача не найдена — код выхода != 0 и сообщение в stderr.

**REQ-11.4** WHEN пользователь выполняет `todushka` без аргументов, the system SHALL запустить TUI и открыть начальный экран `Today`.

### Группа 12 — Навигация и клавиатура

**REQ-12.1** WHEN пользователь нажимает горячие клавиши перехода между системными списками (по умолчанию: `1` — Inbox, `2` — Today, `3` — Upcoming, `4` — Anytime, `5` — Someday, `6` — Logbook), the system SHALL переключить активный список без потери введённых данных в открытых модалках.

**REQ-12.2** WHEN пользователь нажимает `j`/`↓` или `k`/`↑` в любом списке, the system SHALL переместить фокус на следующий/предыдущий элемент списка, не выходя за границы.

**REQ-12.3** WHEN пользователь нажимает `q` или `Ctrl+C` в верхнем уровне TUI, the system SHALL корректно завершить приложение с кодом выхода 0, гарантировав сброс терминала к исходному состоянию.

**REQ-12.4** WHEN пользователь нажимает `?` в любом экране, the system SHALL отобразить контекстный экран помощи со списком доступных в текущем контексте клавиш.

### Группа 13 — Конкурентность и ошибки

**REQ-13.1** WHEN внутри TUI происходит любая ошибка операции с БД (кроме REQ-9.3), the system SHALL показать пользователю сообщение об ошибке в области статус-бара и сохранить технические детали в лог-файл `$XDG_STATE_HOME/todushka/log` (или `$HOME/.local/state/todushka/log`), не завершая приложение.

**REQ-13.2** WHEN происходит panic в обработчике сообщения TUI, the system SHALL восстановить терминал, вывести в stderr краткое сообщение и stack trace в лог-файл, и завершиться с ненулевым кодом выхода.

### Группа 14 — Платформа и терминал

**REQ-14.1** WHEN приложение запускается в терминале, поддерживающем не менее 256 цветов, the system SHALL применить тёмную цветовую тему с цветными акцентами для дедлайнов, тегов и индикаторов статуса.

**REQ-14.2** WHEN приложение запускается в терминале с поддержкой ≤ 16 цветов или с `NO_COLOR=1` в окружении, the system SHALL отрисовать UI монохромным с использованием атрибутов bold/underline вместо цветовых акцентов, не падая.

**REQ-14.3** WHEN приложение собирается под `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, the system SHALL компилироваться без CGO с единым набором исходников и единым `go.mod`.

## Topological Order

```
Группа 9 (storage) → Группа 5 (task editing CRUD) → Группа 3 (areas) → Группа 4 (projects/headings) → Группа 6 (tags) → Группа 8 (today engine) → Группа 7 (repeats) → Группа 2 (system lists) → Группа 1 (quick entry, parser) → Группа 12 (navigation TUI) → Группа 11 (CLI scripting) → Группа 10 (export/import) → Группа 14 (terminal compat) → Группа 13 (errors/concurrency)
```

Reason: persistent storage (gr.9) — фундамент. Сначала domain-CRUD (gr.5) на чистых типах. Areas/Projects (gr.3,4) расширяют модель. Tags (gr.6) и Today Engine (gr.8) — чистые функции поверх модели. Repeats (gr.7) опирается на статусы из gr.5 и на правила Today (gr.8 для проверки следующего экземпляра). Системные списки (gr.2) — query-уровень поверх всего вышеперечисленного. Quick Entry (gr.1) — UI + парсер, использует все нижележащие слои. Навигация TUI (gr.12) собирает экраны. CLI scripting (gr.11) дублирует domain-API без TUI. Export/Import (gr.10) — побочный канал поверх готовой модели. Terminal compat (gr.14) — кросс-сшивка с UI-слоем. Error handling (gr.13) — интеграционный слой, валидируется в самом конце.

## Conflict Priority

**REQ-5.5** (checklist completion не закрывает task автоматически) vs **REQ-4.3** (project автозакрытие при завершении всех task) — нет реального конфликта: REQ-5.5 о checklist→task, REQ-4.3 о task→project, оба правила применяются независимо.

**REQ-9.6** (synchronous commit) vs производительность TUI — компромисс: bbolt fsync на каждое изменение даёт задержку 1–10ms; для интерактивного TUI это приемлемо. Resolution: synchronous commit обязателен; если в v2 начнём упираться — добавим batch commit для bulk-операций (import/export уже batch по природе).

**REQ-1.6** (привязка к проекту в Quick Entry по имени) vs **REQ-3.1** (имена Area уникальны, но имена Project — нет, в Things 3 можно иметь два проекта с одинаковым именем в разных Areas) — Resolution: REQ-1.6 прямо описывает поведение при множественном совпадении (отклонить ввод). Это намеренно строгое поведение в v1; UI с автодополнением и выбором среди дубликатов — deferred.

## Open Design Questions

| Question | Why It Matters | Impacted Requirements |
|----------|---------------|----------------------|
| Какой identifier task показывать в CLI (`todushka complete <task-id>`) — короткий human-readable (`a3f`) или полный UUID? | Влияет на UX скриптинга и на формат вывода всех CLI-команд. | REQ-11.3, REQ-11.1 |
| Как сериализовать `Repeat Rule` в JSON-экспорте — внутренний struct или iCalendar RRULE-совместимый формат? | Совместимый формат упростит будущий импорт из Things 3 / iCal; внутренний — проще. | REQ-10.1, REQ-7.1 |
| Хранить ли `Logbook` неограниченно или вводить retention (например, 1 год)? | Без retention БД будет расти линейно; с retention пользователь может удивиться исчезновению старых записей. | REQ-2.6, REQ-9.4 |
| Разрешать ли `Tag` принадлежать не только к `Task`, но и к `Project`? | В Things 3 это допустимо; в v1 пока не описано в требованиях. | REQ-6.1 (потенциально расширяется) |
| Поведение Today Engine для часовых поясов: фиксируем локальный TZ системы при каждом запуске или сохраняем «creation TZ» у задачи? | Влияет на семантику «сегодня» при переезде между TZ или путешествиях. | REQ-8.1, REQ-8.2 |
| Поведение `NextOccurrence` для `weekly on <weekdays>` когда задача завершена с большим опозданием (например, неделю спустя) — следующий экземпляр = ближайший подходящий день после `completed_at` или после `start_date`? | Влияет на корректность repeating tasks при длительных перерывах. | REQ-7.2 |
| Конкретные горячие клавиши: использовать ли только vim-like (`j/k/gg/G`) или дублировать стрелками + Home/End по умолчанию? | UX-решение; влияет на onboarding. Текущая формулировка REQ-12.2 уже допускает оба. | REQ-12.1, REQ-12.2 |
| Стратегия «pin to today» (REQ-8.3) после смены календарного дня: автоматически снимать `pinned` в полночь или оставлять до явного действия пользователя? | Things 3 сбрасывает в полночь. Влияет на ожидания пользователей Things 3. | REQ-8.3 |
